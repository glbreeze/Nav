n_hist =   0  →  误差   0°

## 3.5 🔴 缓存污染（07-20 发现，推翻了 §4 的推论）— job 14379732

`window_forward` 和 `goal_append_warm` 开头都是 `_inject → clean_kv_cache()`，
而 `stream_state` **没有任何保存/恢复**。所以真实 eval 循环是：

```
append_frame(k)      缓存 = 实时因果流
window_forward       缓存被清空、重建、重放 32 帧
goal_append_warm     缓存再被清空、重放 64 帧 + 目标插在 m+1
append_frame(k+1)    ← 接在"目标预热"的残留状态上，不是流上
```

**实测**（同样 150 帧，A=纯 append，B=每帧后插一次 policy 调用）：
```
frame   A干净流    B插policy   A vs B
   60   0.0000     0.0000     0.0000    ← 第一次 policy 调用之前，完全一致
   71   0.0020     0.4824     0.4824    ← 调用一次后立刻偏 0.48 m
  104   0.0078     0.5430     0.5352
  149   0.0002     0.5234     0.5234    ← 一直维持，不恢复
────────────────────────────────────
max |A − disk| = 0.0078 m      max |B − disk| = 0.6250 m   （偏 80 倍）
```

**含义**：`cur_pose = cache["cam_pose_enc"][k]` —— 机器人"我在哪"的读数，
在真实 eval 里**每一步都是错的**。而 `t_rel = R_cur^T(t_goal − t_cur)` 同时依赖它。

⚠️ **这推翻了 §4 里"位姿不是主因"的推论**。那条基于"ep1 的 n_hist=3 所以位姿准"，
但当时我只验证了 goal_pose，**cur_pose 被污染了却没查**——而冒烟测试恰好是连续
append、不插 policy 调用，所以漏过了。

**这也解释了 12/12 全部不靠近目标**：不是随机学不好，是每步都在错误的自身定位上决策。

### 修复：改成自回归推理（07-20 已实施）

`window_forward` 是**训练路径**的东西——训练没有实时流，只能注入磁盘 cache 重放窗口。
在线推理的流本来就是活的：`append_frame` 上一步已经对该帧做过 `_aggregate_features`，
而 `encode_memory` 只用了 `window_forward` 输出的**最后一行**（`wt[-1]` + `cur_agg`），
其余 31 帧算完即弃。

| 文件 | 改动 |
|---|---|
| `stream_state.py` | `append_frame` 保存已算出的 `agg_tok`；新增 `restore_live()` |
| `memnav_policy.py` | 在线时用 `cache["cur_agg"]`，不调 `window_forward`；`goal_pose` 按 m 缓存 |
| `policy_agent.py` | 传缓存字典、per-episode 清空、goal 重算后 `restore_live` |

**goal_pose 缓存是必需的，不是优化**：`goal_append_warm` 一定会清缓存，原来
`window_forward` 每步重建顺带刷新了它。只做自回归不做缓存，污染会累积。

训练路径未动（`cache.get("cur_agg")` 为 None 时走原逻辑）。

### 走过的弯路：`restore_live` 失败（job 14380096）

第一版想法是"被清空了就用 `window_forward` 重放窗口修回来"。**错的，而且更差**：

```
原始:            max|B−disk| = 0.6250 m   偏差平稳
restore_live:    max|B−disk| = 1.2993 m   偏差持续增长 0.47→1.26
```

原因：**重建本身就是错的**。数据摆在那里——
```
实时流 vs 磁盘预计算    0.0078 m   ← 实时流是准的
window_forward 重建     ~0.5 m     ← 重建偏这么多
```
拿一个偏 0.5 米的东西去"修"，误差只会累积。

⚠️ 那次验证还有个我自己的错误：测试里 `m = k//2`，锚点每两步就变一次，
是最坏情况；真实 eval 里 m 全程不变（ep0=117, ep1=74, ep2=90）。

### 最终解法：KV 快照（job 14380406，✅ 通过）

不重建，**直接把张量存下来再放回去**——空间换时间：

```python
snap = st.snapshot_kv()          # clone 实时 KV
... goal_append_warm 照常清空 ...
st.restore_kv(snap)              # 逐字节还原
```

**实测结果**：
```
frame   A干净流    B插policy   A vs B
   60   0.0000     0.0000     0.0000
   71   0.0020     0.0020     0.0000
  104   0.0078     0.0078     0.0000
  149   0.0002     0.0002     0.0000
────────────────────────────────────
max |A−disk| = 0.0078 m    max |B−disk| = 0.0078 m
```
**`A vs B` 全列 0.0000 —— 逐字节相同，污染彻底消除。**

代价 **8.14 GB 显存**（L40S 48 GB，模型占约 20 GB，余量够），
且只在 m 变化时才 clone —— 稳态下不分配。

三版对比：`0.6250 → 1.2993（修错了）→ 0.0078（✅）`

## 3.6 🔴 07-20 后续：真正卡住机器人的是"输出→动作"这一段

修完缓存污染后重跑，诊断行第一次给出可信的模型方向（坐标轴 bug 也修了）：

```
[diag s15] MODEL fwd=-0.74 dir=-173°  TRUE=-138°   差 35°  ✅
[diag s22] MODEL fwd=-0.68 dir=-177°  TRUE=-137°   差 40°  ✅
[diag s17] MODEL fwd= 0.54 dir=  -9°  TRUE=-138°   差129°  ❌
```

**模型第一次指向后方**（fwd 为负 = 目标在身后）。此前 17 个样本全部落在
−52°~82° 的窄带、从不向后。

⚠️ 诊断仍有一个缺陷：输出为 `(-0.00, -0.00)` 时 `arctan2(0,0) = -180°`，会
碰巧被判成 agree。**零向量没有方向，这类 agree 必须剔除**。上面 3 条是剔除后的。

### 但机器人 25 步只走了 0 米（`path=0.0`）— 三个原因叠加

**① 我加的 `<0.5 清零` 是纯负作用**（`memnav_policy.py`）：
```python
traj[traj_len < 0.5] *= [[0.0, 0.0, 1.0]]     # 置零 x,y，保留 yaw
```
而驱动代码（`eval_revisit_habitat.py:405-408`）**只读 x,y**：
```python
fx, lat = pts3[:,0], pts3[:,1]        # 第 2 通道 yaw 从来不用
W = pos + fx*fwd + lat*lft            # 全 0 → 所有路点 = 当前位置
```
→ MPC 跟踪"原地不动"的路径 → v=0。**我想保留的转向信息根本没人读。**

**② 而且不触发提前退出**：判定停止的条件是 `abs(pts3).max() < 1e-3`，
yaw 非零就不满足 → 白跑满 120 步。

**③ MPC 硬性不能倒车**（`mpc_tracking.py:68`）：
```python
opti.subject_to(opti.bounded(0.0, v, v_max))
```
所以"目标在身后"必须先原地转 180°，`w_max=1.2 rad/s × DT=0.1` → 每步最多
6.9°，**至少 26 步**才能转过来。

### 另一条被推翻的旧结论：`SR=0.625` 不是模型能力

novel eval（`14183499`）5 次成功的步数是 **14 / 28 / 30 / 35 / 37**，
全部 **< anchor_margin=39** —— policy 要到第 39 步才接手，之前是 warmup 直行。
而 56 条 diag 行**全部**是 warmup 占位值 `fwd=0.00 lat=0.10`：
```
$ grep -c "MODEL fwd=0.00 lat=0.10" log   # 56
$ grep -c "\[diag s" log                  # 56  → 无一例外
```
**这 5 次成功是机器人直着开撞上目标的，policy 一次都没参与。**
SPL=1.000 也对得上——直线本来就是最优路径。3 次失败的都跑满 200 步（policy 接手后）。

→ **不能把 `SR=0.625` 当模型性能报告**，它测的是"目标恰好在正前方"的比例。
→ 也解释了 revisit eval 为何两条件都 0：leg1 已灌 150~220 帧，k 从第 0 步就 ≫ 39，
   policy 立刻接手，没有直行送分的机会。

## 4. 还不知道的：SR=0 的主因

⚠️ **本节的推论已被 §3.5 推翻，保留以记录推理过程。**

当时认为**位姿不是主因**，反例：

| episode | m | n_hist | 位姿 | 方向 | 结果 |
|---|---:|---:|---|---|---|
| ep0 revisit | 117 | 46 | ❌ 错 | ❌ 错 | SR=0 |
| **ep1 revisit** | **74** | **3** | **✅ 准** | ❌ **仍错** | SR=0 |

**错在哪**：ep1 的 `n_hist=3` 只说明 **goal_pose** 准，而 `cur_pose` 同样被污染
（§3.5），所以"位姿准了方向还错"这个前提根本不成立。

**剩下的候选：策略还没学会条件导航。** 证据：

```
模型输出方向     −52° ~  82°     （始终这个窄带）
revisit 真值    −171° ~ 152°     agree 0/17
novel   真值      49° ~  70°     agree 9/12
```

⚠️ **novel 那组不能作为对照**——它的真值 std 只有 7.9°，几乎是常数，
模型本来就爱输出 ~70°，"对"很可能是撞上的。**这个判断需要更多 episode。**

背景：训练等效 **~2000 / 16710 步（12%）**，`sep` 从 0.087 涨到 0.61 且无平台，
`gate_seen` 刚突破 0.5 到 0.69。"策略还没学会"与训练曲线自洽。

## 6. 修好位姿后怎么重训（不用从头）

ckpt 是按模块命名的 state_dict，可选择性冻结：

```
module            张量数      参数量
novel               184  27,246,720   不吃 pose，不受影响
decoder             144  18,932,736   间接受害，建议重训
compress_rgbd/depth  16   9,633,792   不受影响
retrieval             7     524,803   ✅ 已训好，冻结保护
revisit_merge         4      19,976   ❌ 重训（只有 2 万参数）
```

**推荐**：冻结 `retrieval`/`novel`/`compress_*`/`proj_*`，只训 `revisit_merge` + `decoder` + `action_head`。
理由：decoder 很可能已学会忽略 revisit token（那一路长期是噪声），只训 revisit_merge 不够。
